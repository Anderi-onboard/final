# 工作流：从一卦到一段解读

这份文档是流水线的操作说明。每一步写明：谁做（程序还是模型）、输入输出、
用什么测试守着、当前状态。状态只写“已测”或“未做”，不写“应该可以”。

## 总览

```
投卦 ─→ ① 排盘（程序）─→ ② 卦况包 ─→ ③ 关系/状态（程序）─→ ④ 检索（程序）
                                                              │
        ⑤ 理解问题（模型1）←── 用户问题 ───────────────────────┤
                                                              ▼
        ⑥ 依书套用（模型2，每条命中条目一次）─→ ⑦ 旁证判断（模型3）
                                                              │
        ⑧ 综合（模型4）←──────────────────────────────────────┘
                                                              ▼
                                                     解读（附覆盖账本）
```

一个模型只管一步逻辑。程序能算的，不交给模型。

## 各步

### ① 排盘（程序）— 已测
- 输入：六个爻（阴阳、动）、起卦时间。输出：完整棋盘（`vendor/liuyao-engine.js`）。
- 测试：`test/casting.mjs`、`test/kb-rules.mjs`、`test/kb-packet.mjs`。
- 书中卦例：`test/book-cases.mjs`（目前 1 个卦例，8 条断言）。

### ② 卦况包（程序）— 已测
- 输入：棋盘、可选用神。输出：`packet`（六亲、旺衰、空、破、冲合、进退、伏飞、动变、神煞、
  候选神煞、用神视角、关系与状态、检索 token）。
- 测试：`test/kb-packet.mjs`、`test/kb-render.mjs`（每个字段都必须进入文字，否则红）。

### ③ 关系与状态（程序）— 已测，“有力”待用户确认
- 关系：冲、合、刑、生、克，且至少一端在用神链上（用神、元神、忌神、仇神）。
- 状态：每爻的旺衰、空、月破、日冲、动；“有力”是暂定判据，带 `provisional` 标记。
- 测试：`test/facts-split.mjs`。

### ④ 检索（程序）— 已测
- 规则：条目的 `when` 全部命中、`unless` 一个都不命中，才算适用。
- token = 棋盘特征 ∪ 关系/状态 token（见 `src/packet.js`）。
- 覆盖账本：每个 token 要么有条目引用，要么列为“未落位”，两者之和必须等于 token 总数。
- 测试：`test/kb-retrieval.mjs`（语法 + 实测词汇）、`test/kb-ledger.mjs`（守恒）、
  `test/kb-entries.mjs`（每条条目在它该命中的棋盘上命中，且只在那些棋盘上）。

### ⑤ 理解问题（模型1）— 未接入
- 输入：用户问题。输出：主体（自占/代占、谁）、意图、前提、风险、语气。
- 契约：`src/pipeline/contracts.js` 的 `UNDERSTAND_SPEC`；提示词：`src/pipeline/prompts.js`。
- 测试：`test/pipeline.mjs`（用 scripted 模型，验证输出格式与重试）。
- 未做的部分：真实模型调用、用神选择的端到端验证。

### ⑥ 依书套用（模型2，每条命中条目一次）— 未接入
- 输入：一条命中的条目（原文 `text_zh`）、卦况包中与它相关的部分。输出：这条原文对这卦意味着什么。
- 规则：只能引用条目里的原文；推断要标明是推断。
- 契约：`CLAIM_SPEC`。测试：`test/pipeline.mjs`（scripted）。

### ⑦ 旁证判断（模型3）— 未做
- 输入：问题的逻辑链（用神、元神等）、状态类 token、没有进入用神链的关系。
- 输出：哪些旁证在逻辑上贴近这个问题，理由是什么。
- 规则：旁证单列，不冒充用神论证。

### ⑧ 综合（模型4）— 未做提示词改写
- 输入：理解结果、各条断语、旁证、覆盖账本（列出未落位的 token）。
- 规则：以用户提出的实际逻辑为主；用神论证在前；旁证单列；没有书中依据的写明是推断。
- 契约：`SYNTH_SPEC`。提示词需要按这些规则改写。

## 怎么加一批知识库条目

1. 选一条原文规则句，只选正文（野鹤、觉子、古法），不选乾按、编者按。
2. 把它的整行（原文）加进 `knowledge/sources/*-excerpts.json`，记下行号。
3. 写成条目：`text_zh` 必须是那行的子串，`when` 只用 `src/features.js` 或 `src/facts.js`
   能发出的 token，`unless` 用于排除。
4. 跑 `node scripts/run-tests.mjs`。`kb-entries.mjs` 会检查：是否逐字、是否在该命中的棋盘上命中、
   是否只在那些棋盘上命中。
5. 位置类 token（如 `L3:dayClash`）让一条规则要展开成六条。展开后的条目用同一个 `text_zh`，
   这是有意的，不是重复。

### 第三批发现的两处（已修 / 待查）

- **已修：合好的条件与原文相反。** 卦况包原来让“两爻都不动”算合好；原文 L1330“爻动与动爻相合”、
  L1324“但有一爻不动，亦不为合”都说明合好要两爻都动。合起也去掉了“与动爻相合”的情况，原文只有“与日月动爻合”。
- **待查：化扶只在第 1、4 爻出现。** 2、3、5、6 爻的化出地支从来不和原地支构成六合（实测 8×64 组合）。
  这可能是纳甲变化的真实结果，也可能是引擎的变化规则有缺口。我没有能从原文确认，所以四条化扶条目保留，
  并列入 `kb-retrieval.mjs` 的 `ENGINE_NEVER_EMITS` 明确例外，例外名单由测试校验，引擎一改就会变红。

### 测试的一个教训（第二批发现）
`kb-retrieval.mjs` 原本只在十月的十二天上测词汇，月建只有酉和戌两个，所以 `L4:monthClash` 从未被看到，
一条正确的月破条目会被当成拼写错误拒掉。现在词汇表也在每个月取样，`kb-entries.mjs` 同样每月取样。

## 已知的局限

- 位置类 token 会让条目数膨胀（一条规则 ×6 或 ×12）。等条目数量上来后，再考虑加
  “任一爻”一类的通配 token。这一点不急，现在先保证每条都对。
- 书中的“问题依赖”规则（如“久病”“近病”）：问题类型不在棋盘里，目前不能用 token 表达，
  需要先把问题类型也做成 token，这一步还没做。
- “有力”判据未经用户确认。
