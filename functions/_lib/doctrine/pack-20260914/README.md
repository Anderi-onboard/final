## 一、别名表:31 条接上了,3 条留 null

包里写着「当前包没有伪造 `project_feature`……字段绑定必须由代码方对照当前提交完成」。
这边照同一条规矩办:**填不上的留 null,不编。**
填一个不存在的检索键,那条判据永远命中不了 —— **而且不报错**。

| | 条数 | |
|---|---|---|
| `bound` | 24 | 仓库同名发得出来 |
| `bound_renamed` | 2 | 旺相/休囚死 → `TARGET_STRONG` / `TARGET_WEAK`(仓库只对**用神**发,对任意一爻发等于恒为真) |
| `bound_from_m1` | 5 | 不是盘上的事实,由 M1 从问题里读 |
| `blocked` | 3 | `MOVING_TOMB` · `OPEN_TOMB_BY_CLASH` · `AT_ABSOLUTE` |

那 3 条是**引擎真的算不出来**:动墓(入动爻之墓,和化墓不是一回事)、冲墓(冲开墓库)、
临绝(爻临自己的绝地,和「化绝」不是一回事)。要接就得先在
`liuyao-relations.js` 里把这三个事实算出来,不是在这张表上补个名字。

## ⭐⭐ 二、接这张表的时候发现的:映射表短了一截,引擎早就算出来了

对着 34 条核了一遍,**21 条在 `liuyao-features.js` 里没有落点** —— 而其中绝大多数
`liuyao-relations.js` **一直在算**:真空/假空/真破/假破/暗动/化空/化绝/回头冲/回头合
全在 `state` 和 `transforms[].kinds` 里,只是那张映射表没往外发。

也就是说:**46 条判据引用的检索键有三分之二找不到地方落,不是因为引擎读不出来,
是因为一张映射表短了一截。** 而一张没同步的映射表不会报错 —— 它只让下游永远
检索不到那一类卡,下游照样有卡可读。这是本仓库反复付钱的那个形状。

已补齐(`tests/feature-vocab.mjs` 守着不许再出孤儿):
- **真/假分开发**,不许合成一个 id:真空是「这条线死了」,假空是「它还在,只是现在不出面」——
  两条相反的断法路由到同一批卡上就是白路由。
- **三种墓各自也发自己的 id**:日墓待冲、月墓待出月、动墓随动爻,SOP-5 恰恰按这个分尺度。
- **「化绝」从 `AT_ABSOLUTE` 改名成 `TRANSFORM_ABSOLUTE`。** 那是两件事:
  临绝是「这一爻在绝地」,化绝是「它动了,动成了自己的绝」——
  后者是《增删卜易》§3 写死的大凶败局。混成一个 id,那条败局检索不到自己的卡,
  **而页面上什么都看不出来**。`AT_ABSOLUTE` 一直是这边起错的名字,包里的规范名是后者。

实测那副考试盘:补齐前发 15 个 feature,补齐后 17 个,新出来的两个正是
`TRANSFORM_ABSOLUTE` 和 `RETURN_CLASH` —— **就是这副盘上断错的那一条**。
